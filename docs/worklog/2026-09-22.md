## Windows rmtree 버그 수정 (M6과 무관, 사용자 요청으로 바로 처리)

## 원인
`features/repos/services.py`의 `services_repo_clone`이 `shutil.rmtree(dest, ignore_errors=True)`로 이전 클론 폴더를 지우는데, git의 `.git/objects` 안 pack 파일이 Windows에서 읽기 전용으로 남는 경우가 있어 삭제가 조용히 실패하고(`ignore_errors=True`라 예외를 안 던짐) 폴더가 그대로 남는다. 다음 배포 때 같은 경로로 `git clone`하면 "destination path ... already exists and is not an empty directory"로 실패한다.

## 수정
`shutil.rmtree`에 `onexc` 핸들러(Python 3.12+ 권장 API, 이 프로젝트 venv가 3.12.14)를 추가 — 실패한 파일의 읽기 전용 속성을 `os.chmod`로 풀고 재시도. `services_repo_clone` 안에 중첩 함수로 뒀다 (`services_repo_tree`의 `walk`, `services_repo_collect`의 `read_file`과 같은 이 파일의 기존 패턴).

## 검증

## 테스트 인프라 삽질 (진짜 버그 아님, 하지만 중요)
`tests/test_watches.py`에 웹훅 테스트를 추가하면서 디바운스가 실제 `asyncio.Task`를 띄우는 테스트들을 섞었더니 **간헐적으로** `sqlalchemy.exc.OperationalError: database is locked`가 다른 테스트의 fixture 셋업(`DROP TABLE`)에서 터졌다.
- 원인 추정: 이 프로젝트 테스트는 `pytest-asyncio`의 기본값(`function` 스코프)대로 테스트마다 새 이벤트 루프를 쓰는데, `shared/database.py`의 `async_engine`은 모듈 하나에 딱 한 번만 만들어져서 전체 테스트가 공유한다. 지금까지의 테스트는 전부 자기 안에서 끝나는 코루틴만 썼는데(백그라운드 태스크 없음), watches 테스트는 처음으로 `asyncio.create_task`로 테스트 함수 경계를 넘나드는 타이머를 만들었다 — 취소하고 `await`까지 해도, 그 커넥션 풀 커넥션이 이전 루프에 묶인 채 다음 테스트의 새 루프로 넘어가면서 상태가 꼬인 것으로 보인다.
- 시도했다가 버린 것: `async_engine.dispose()`를 매 테스트 `client` 픽스처 시작 시 호출 — 오히려 멈춰버렸다(타임아웃, 백그라운드로 넘어감. `TaskStop`으로 강제 종료).
- 실제 해결: `test_watches.py` 파일 전체를 `pytest.mark.asyncio(loop_scope="module")`로 이벤트 루프 하나만 쓰게 만들었다 — 이 파일의 테스트 전부가 실제 서버처럼 루프 하나를 계속 쓰는 모양이 되면서 문제가 사라졌다. 5번 연속 실행 + 전체 스위트 2회 연속 실행으로 안정성 확인.
- 개별 테스트에서도 방어적으로 정리하도록 `clear_debounce_tasks` autouse 픽스처(테스트 전후로 남은 태스크 취소+대기)를 추가해 이중으로 막아뒀다.
