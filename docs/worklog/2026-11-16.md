## Non-root Dockerfile templates
- Owner asked about randomizing the internal port for security; assessed as ~no benefit (ALB 443 is the only public surface; breaks repos that hardcode ports). Did non-root execution instead.
- `Dockerfile_Service.services_dockerfile_user_block`: after install+build (as root) `chown -R <user> /app` + `USER <user>` (Node `node` uid 1000, Python `useradd app` uid 10001). Ports < 1024 stay root (cannot bind as non-root). `{user_block}` added to both templates. Not applied to repo-supplied Dockerfiles or LLM raw Dockerfiles (experimental languages).
- Verified locally with docker: Node + Python images build (linux/amd64), run as uid 1000 / 10001, respond 200, app can write to /app at startup. No AWS touched. Trade-off: `chown -R /app` adds a layer roughly the size of /app (node_modules) -> larger image/push.
- Not verified: a real AWS deploy of a non-root image; Next.js-style apps writing caches (covered by chown -R, untested); repos that bind a port < 1024 stay root by design.

## Cost confirmation backend (branch `feat/cost-backend`)
Spec `docs/superpowers/specs/2026-11-16-cost-confirm-design.md`, plan `docs/superpowers/plans/2026-11-16-cost-backend.md`, tasks 1-7. No AWS touched; all tests use fake price files / fake Express.

Built:
- T1 `features/pricing` price reading: public bulk files (`AmazonECS`, `AWSELB`) per region, 24 h disk cache in `data/cache/pricing-<region>.json`, stale cache on fetch failure, `None` when nothing. ALB/LCU rows picked by regex (skips Outposts/TS/Reserved rows); region validated before it enters URL/cache path.
- T2 estimate: Fargate (vCPU + GB) + ALB fixed hourly; periods 1 h / 24 h / 168 h / 730 h; 4 presets (256/512, 512/1024, 1024/2048, 2048/4096); ARM64 hourly + saving % (display only); scaling validation (`MAX_TASKS_CAP`=4).
- T3 `GET /api/pricing/options`, `POST /api/pricing/estimate` (400 bad input, 503 no price table); `Advice_Cost` extended, filled after the advice cache on a copy.
- T4 deploy options `cpu`, `memory`, `min_tasks`, `max_tasks`, `scale_metric`, `scale_target`, `planned_hours` + `running_since`, `plan_notified_at` on `deploys` (`ENSURE_COLUMNS`); create-time validation; PATCH settings `planned_hours` (null clears; every send re-arms the alert); Express create sends `cpu`/`memory`/`scalingTarget` only at service creation, redeploy/recovery `update` sends none.
- T5 notification kind `plan_exceeded` (notification only, no auto stop/delete): `services_deploy_plan_check` + `services_health_plan_notify`, called from the health monitor loop after the health pass in its own try/except.
- T6 MCP `deploy` takes the new options; preview shows cost lines (`/api/pricing/estimate`), "price unavailable" line when the table is missing.
- T7 docs (architecture, features, aws-notes, milestones, `.env.example`, HISTORY) + one full-suite run.

Decisions / rulings:
- `running_since` rule changed after review: set only when NULL on reaching `running`; cleared on stop, delete, and failure with no `service_arn`. A git-push auto-redeploy (running -> queued -> running) and a failed redeploy of a live service keep the clock; resetting would hide billing that continues.
- Cost is computed after the advice cache (on a copy), never stored in the cache, so a price change cannot serve a stale number.
- Default spec (no cpu/memory) is priced as 256/512 per botocore 1.43.126 and flagged "unverified default" in the response.
- Autoscaling is a user-chosen AWS `scalingTarget` applied at creation, not an automatic action by this system (Hard rule 3 unchanged).
- Plan alert existing-DB caveat: `notification_settings.kinds` rows created before this change lack `plan_exceeded`, and the filter drops unknown kinds, so the alert stays OFF on the existing DB until kinds is PATCHed. No migration (cannot tell muted from predating). Web/app settings UIs still list six kinds, so a toggle PATCH would drop it; fix is the first task of the web plan.
- `HEALTH_MONITOR_ENABLED=false` also disables the plan alert (same loop); documented in `.env.example` and architecture.
- Running deploys that predate the columns have `running_since` NULL, so they never trigger the plan alert.

Arithmetic correction: default spec hourly = 0.25*0.04656 + 0.5*0.00511 + 0.0225 = 0.036695 -> one month (730 h) = 26.787 -> 26.79 (the plan's 26.78 was a slip; tests and docs use 26.79).

Price observation (ap-northeast-2, 2026-11-16, not hard-coded): Fargate x86 vCPU 0.04656/h, GB 0.00511/h, ALB 0.0225/h, LCU 0.008. Recorded in `docs/aws-notes.md` as a dated observation.

Docs: botocore 1.43.126 says `cpu` = CPU units string, `memory` = MiB string, Express default 256 / 512; old note said 1 vCPU / 2 GB -> CONFLICT recorded, default marked unverified. Also closed the "address same after restart?" item: it is not (observed 2026-11-15).
