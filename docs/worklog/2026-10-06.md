## `aws login` profile support

Question from owner: can accounts be connected via OAuth?
- GitHub: yes, GitHub App install flow is already redirect-based (user-auth add-on possible, not done).
- AWS: no third-party OAuth consent. Cross-account stays AssumeRole+ExternalId (M6). For the dev's own account, `aws login` (console sign-in, OAuth 2.0 + PKCE handled by AWS CLI) replaces access keys. Owner chose this.

### Verified (source: installed botocore 1.43.98 + AWS CLI user guide "Login for AWS local development using console credentials")
- `botocore.credentials.LoginProvider` exists; triggers on `login_session` key in the profile. Chain order: env -> assume-role -> web identity -> sso -> shared credentials file -> **login** -> process -> config.
- Needs `awscrt` (`botocore.compat.EC`); without it `MissingDependencyException: ... pip install "botocore[crt]"`. Was not installed -> installed awscrt 0.36.0, boto3/botocore stayed 1.43.98.
- Token cache: `~/.aws/login/cache/<sha256(login_session)>.json`, override `AWS_LOGIN_CACHE_DIRECTORY`. Required fields: `accessToken{accessKeyId,secretAccessKey,sessionToken,accountId,expiresAt}`, `refreshToken`, `dpopKey`, `clientId`.
- Refresh = `signin.CreateOAuth2Token` (unsigned + DPoP header) against the **session region** endpoint; offline resolve gives `https://signin.ap-northeast-2.amazonaws.com`.
- Docs: AWS CLI >= 2.32.0; root needs nothing, IAM user/role needs managed policy `SignInLocalDevelopmentAccess`; refresh every 15 min, session max 12h.

## Connection blocks

- Owner: "GitHub has to be connected per AWS, so make the two one block, with a + that adds a block each time."
- Model: new table `connections` rather than a column on `aws_accounts` — `create_all` adds new tables but cannot alter existing ones, and a DB reset would lose the live connection. A block can exist empty (created by `+` before either side is connected). Several blocks may point at the same GitHub installation (one installation per GitHub account), so block delete removes the block's AWS account record but leaves the installation; "연결 해제" on the GitHub row only unlinks.
- Linking a fresh GitHub install to the block that started it: `install-url?c_id=N` -> `.../installations/new?state=N`; callback reads `state` and links. If GitHub does not return `state` (not verified against real GitHub, e.g. the "already installed -> Save" path), the installation is still stored and the block offers it in "이미 연결한 GitHub 선택".
- Backfill in `services_connection_get_all` (a GET that writes, once): AWS accounts without a block get one; when there were no blocks and exactly one orphan AWS account and one installation, they are paired. Real DB after restart: block 1 `test` = AWS `<aws-account-id>` verified + GitHub `kjfcvx12` active.
- UI: `AccountsPage.jsx` rewritten around blocks (same guide-window flows, now started per block; `run()` helper for busy/error), `AccountPicker.jsx` is one select of blocks and still feeds `aws_account_id`/`github_installation_id` to the deploy form, so deploys API is unchanged.
- Tests: `test_connection_block_flow`, `test_connection_backfills_existing_aws_account`, `test_connection_backfill_pairs_single_aws_and_github`. 131 pass. Build OK. Headless capture (list GET mocked only to append a second empty block): second block shows `[AWS 연결]`, select, `[GitHub 연결]`; deploy form picker option "test — AWS <aws-account-id> · GitHub kjfcvx12".
- Old endpoints (`POST /aws`, list/delete per kind) kept; the UI no longer calls `POST /aws` or `DELETE /github/{g_id}`. No UI path removes a GitHub installation record now (only unlink).
