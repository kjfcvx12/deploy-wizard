## GitHub token bug found by a real check

- Owner asked whether private repos just work once the install is set to All repositories. Checked for real instead of answering from the design: listed the installation's repos and tried a branch lookup with and without the app token.
- Raw symptom: every lookup with the token -> `GitHub 연결이 끊어졌습니다. 다시 설치해 주세요.` while the same repos resolved fine without a token.
- Cause: `deploys.github_installation_id` holds our `g_id` (1) but was passed straight to `POST /app/installations/{installation_id}/access_tokens`, which needs GitHub's id (168503578). Three callers: `pipeline.py` clone step, `services_deploy_get_remote`, `watches` polling. Since yesterday's picker change pre-selects the single block, every deploy from the UI would have hit this.
- Fix: `Github_Service.services_github_token_by_g_id(db, g_id)`; callers switched; `services_deploy_get_remote` now takes `db` (router passes it). Tests that stubbed `services_github_installation_token` at the callers now stub the new function, and `test_github_token_by_g_id_uses_github_installation_id` checks the translation itself (g_id != installation id, unknown g_id -> ValueError).
- Real after fix: install is `all`, 29 repos readable, **0 private** — the account has no private repo, so token-authenticated access to a private repo is still unverified. Token-authenticated `ls-remote` on a public repo works.
- Lesson (same as the ECS role ARN bug): stubbing a whole boundary function in pipeline tests hides argument-meaning mistakes; keep at least one test per boundary that checks what is passed across it.

## Private repo verified (E7), token left in `.git/config`

- Owner created `kjfcvx12/private-test`. Installation now lists 30 repos, 1 private. With the app token: branch lookup ok, shallow clone ok (`5ff7ac9`, `README.md`), token not in the clone log lines.
- First control ("no connection") unexpectedly succeeded. `-c credential.helper=` was not enough; this PC has `credential.helper manager` (Git Credential Manager holding the owner's GitHub login). With `GIT_CONFIG_NOSYSTEM=1` + empty `GIT_CONFIG_GLOBAL` + `GIT_TERMINAL_PROMPT=0`: no-credential run is refused, token-only run succeeds. So the token is what grants access.
- Consequence to remember: on this PC, a deploy with "연결 안 함" can still clone the owner's private repos through GCM. Not a product behaviour; our git calls do not isolate ambient credentials. Not changed.
- Found: after `git clone https://x-access-token:<token>@github.com/...`, the token stays in `<work>/deploy_N/.git/config`. Default `.dockerignore` (with `.git`) is only written when the repo has none, so a repo with its own `.dockerignore` and `COPY . .` could bake the token into the image. Fix: `services_repo_clone` runs `git remote set-url origin <clean url>` after a token clone. Verified on the real clone: `.git/config` has `url = https://github.com/kjfcvx12/private-test`, no token. Test extended (`test_repo_clone_uses_token_in_url`). Repo + pipeline tests 32 pass.
- Still against hard rule 6 as written: the token is in `git clone`'s argv (existing design from M6 step 8). Would need a credential helper/askpass via env to remove. Not changed; flagged to the owner.
