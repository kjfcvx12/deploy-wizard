## D. 운영·복구 (2단계)

| ID | 기능 | W | A | 상태 | 동작 |
|---|---|---|---|---|---|
| D-01 | 상태 감시 | 서버 | 서버 | 신규 | 서버 백그라운드 태스크가 `running` 배포의 공개 주소를 주기적으로 GET. 결과는 `health_checks`에 쌓는다 |
| D-02 | 인시던트 생성 | 서버 | 서버 | 신규 | 연속 실패가 기준(기본 3회)을 넘으면 `incidents` 행을 `open`으로 만든다 |
| D-03 | 원인 수집 | 서버 | 서버 | 신규 | 서비스 배포 상태·이벤트와 컨테이너 로그의 끝부분을 모은다 (`mask_text` 통과). 수집 호출은 `aws-notes.md` 검증 후 사용 |
| D-04 | 원인 설명 | 서버 | 서버 | 신규 | 순서: 규칙 표(알려진 패턴) → 시그니처 캐시 → **운영 에이전트**(D12) → 기본 안내. 에이전트는 읽기 도구(헬스 이력, 서비스 이벤트, 로그 끝부분, 배포 버전 목록)로 조사하고 `Incident_Explain`(요약, 원인, `fix_where`, 조치)을 낸다. 반복 상한이 있고, 로그 안의 지시문은 따르지 않는다. AI를 못 쓰면 규칙 표 결과와 기본 안내 |
| D-04a | 에이전트의 행동 | 서버 | 서버 | 신규 | 에이전트가 "재시작" 또는 "되돌리기"를 요청하면 코드가 자동 복구 스위치, 열린 인시던트, 시도 횟수, 대기 시간을 확인한 뒤에만 실행한다. 그 밖의 행동 도구는 없다. 실행한 시도는 `recovery_actions`에 사유와 함께 남긴다 |
| D-05 | 자동 복구 | 서버 | 서버 | 신규 | 규칙 표가 정한 순서로 시도: ① 재시작(같은 이미지로 서비스 갱신) ② 안 되면 이전 정상 버전으로 되돌리기. 각 시도는 `recovery_actions`에 남긴다. 사양 변경·삭제는 하지 않는다 `[가정]` |
| D-06 | 복구 확인 | 서버 | 서버 | 신규 | 복구 후 일정 시간 동안 헬스가 정상이면 `resolved`. 끝내 안 되면 `needs_action` |
| D-07 | 인시던트 화면 | ● | ● | 신규 | 무슨 일이 있었는지 시간순(감지 → 시도 → 결과), 원인, 고칠 곳, 버튼 |
| D-08 | 헬스 이력 | ● | ● | 신규 | 최근 24시간 정상/실패 막대 |
| D-09 | 배포별 자동 복구 스위치 | ● | ● | 신규 | 끄면 감지와 알림만 하고 복구는 하지 않는다 `[가정]` |

**복구 규칙 요약** (코드가 정하고 AI는 고르지 않는다)

| 감지 | 시도 순서 | 이유 |
|---|---|---|
| 헬스 연속 실패 | 재시작 → (실패 시) 되돌리기 | 가장 가벼운 것부터 |
| 새 버전 배포 직후 실패 | 바로 되돌리기 | 직전 변경이 원인일 가능성이 큼 |
| 이전 정상 버전이 없음 | 복구하지 않고 알림만 | 되돌릴 곳이 없다 |

## H. 환경변수 감지·입력 (1~2단계, 웹·앱 공통)

**왜 필요한가.** 진짜 `.env`와 키 파일은 GitHub에 올라가지 않는다. 그대로 배포하면 환경변수가 필요한 앱은 시작하다 죽는 경우가 많다. 마법사는 시크릿 파일을 읽지 않고(규칙 5, 6), **소스에서 변수 "이름"만** 찾아 사용자에게 값을 받는다.

| ID | 기능 | W | A | 상태 | 동작 |
|---|---|---|---|---|---|
| H-01 | 이름 찾기 (코드 패턴) | 서버 | 서버 | 신규 | 판별 단계(`analyzing`)에서 소스를 훑어 환경변수 **이름**을 뽑는다. Python: `os.environ[...]`, `os.getenv(...)`, pydantic-settings 필드. Node: `process.env.X`, `process.env["X"]`, `import.meta.env.X`. 이름이 글자 그대로 있으면 표준 이름이 아니어도 찾는다. 값은 읽지 않는다 |
| H-02 | 이름 찾기 (보조 파일) | 서버 | 서버 | 신규 | `docker-compose.yml`의 `environment:` 이름, `.env.example`/`.env.sample`이 있으면 이름과 기본값 힌트, README의 설명. **값은 버린다.** `.env.example`은 현재 제외 필터(`.env.*`)에 걸리므로 "이름만 읽는 예외"가 필요하다 (규칙 5 수정, 구현 시 함께) |
| H-03 | 필수 여부 판정 | 서버 | 서버 | 신규 | 코드에 기본값이 있으면(`getenv("PORT", 8000)`) `required=false`, 없으면 `true` |
| H-04 | 종류 분류 | 서버 | 서버 | 신규 | ① 규칙: 그 변수를 받는 코드 한 줄의 라이브러리로 판단(`create_engine`=DB, `redis.from_url`=캐시, `stripe.api_key`=결제 등). ② 규칙으로 모르면 그 줄 앞뒤 몇 줄만 AI에 보내 **정해진 목록에서 고르게** 한다 (`database/cache/external_api/secret/config/unknown`). ③ 그래도 `unknown`이면 사용자가 버튼으로 고른다 |
| H-05 | 입력 화면 | ● | ● | 신규 | 찾은 이름을 "꼭 필요해 보이는 것 / 기본값이 있어 비워도 되는 것"으로 나눠 보여 준다. 값 입력, [건너뛰기], 변수 직접 추가. 시크릿 종류는 가려서 받는다 |
| H-06 | 값 보관 | 서버 | 서버 | 신규 | 시크릿 값은 **우리 DB에 평문으로 두지 않는다.** 사용자 AWS 계정의 보안 저장소에 넣고 서비스는 그 참조만 쓴다 (`D8`). 일반 설정값만 서비스 설정에 직접 넣는다 `[가정]` |
| H-07 | 입력 대기 | 서버 | 서버 | 신규 | 빌드·푸시는 환경변수 없이 진행하고, `deploying` 직전에 값이 없는 필수 변수가 있으면 멈추고 입력을 요청한다 (`D9`). 입력을 마치면 [이어서 배포]로 `deploying`부터 재개하고 이미지는 다시 만들지 않는다 |
| H-08 | 실패 후 보완 | 서버 | 서버 | 신규 | 이름을 놓쳐서 앱이 죽으면 에러 해설 규칙 표가 `KeyError: 'X'`, `X is not defined`, `Missing required` 같은 흔적에서 빠진 이름을 뽑아 입력 화면으로 이어 준다 |
| H-09 | 값 보호 | 서버 | 서버 | 신규 | 입력한 값은 응답에 다시 돌려주지 않는다 (`has_value`만). 로그, AI, 메일, 푸시, 에러 해설에 나가지 않는다 (`mask_text` + 값 자체를 기록하지 않음). 배포 삭제 시 우리가 만든(태그된) 보안 저장소 항목도 정리한다 |
| H-10 | 값 수정·삭제 | ● | ● | 신규 | 값을 바꾸거나 지울 수 있다. 바꾼 뒤에는 [다시 배포]가 필요하다고 알린다 (자동 재배포 안 함, 규칙 3) |

**찾지 못하는 경우** (정직하게 알린다): 이름을 코드가 조립할 때(`environ[prefix + "_KEY"]`), 설정 파일을 통째로 읽을 때(`dotenv_values()`, `config.yaml`). 이때는 H-08(실패 후 보완)과 변수 직접 추가(H-05)가 보완한다. 화면에도 "자동으로 찾지 못한 변수가 있을 수 있습니다"를 표시한다.

**AI의 역할 제한**: 분류 한 건당 입력은 변수가 쓰인 줄 앞뒤 몇 줄뿐이고, 출력은 고정 목록 중 하나다 (규칙 4). 값은 보낼 수도 없다 (읽지 않으므로).

## I. 배포 수준·비용 추천 (1단계, 웹·앱 공통)

**목적.** 배포하기 **전에** 레포를 읽고 "이 앱은 이 정도 사양이 맞고, 대략 이만큼 든다, 이런 것이 더 필요하다"를 알려 준다. 사용자는 결과를 보고 배포할지 정한다 (규칙 3의 "만들기 전 확인"과 맞는다).

| ID | 기능 | W | A | 상태 | 동작 |
|---|---|---|---|---|---|
| I-01 | 분석만 하기 | ● | ● | 신규 | 주소를 넣고 [분석]을 누르면 레포를 읽기만 한다 (배포 기록을 만들지 않음, AWS 호출 없음). 같은 `레포+커밋`은 캐시해서 [배포] 때 다시 클론하지 않는다 `[가정]` |
| I-02 | 신호 수집 | 서버 | 서버 | 신규 | 아래 "읽는 곳" 표대로 규칙이 신호를 모은다. AI 호출 없음 |
| I-03 | 수준 판정 | 서버 | 서버 | 신규 | 신호를 점수 표(규칙)에 넣어 `small / medium / large` 중 하나를 고른다. 판정은 코드가 하고 AI는 고르지 않는다 (규칙 4) |
| I-04 | 필요한 것 알림 | 서버 | 서버 | 신규 | 사양과 별도로 "DB가 필요해 보임", "백그라운드 작업이 있음", "환경변수 N개 입력 필요", "파일을 디스크에 저장함(재시작하면 사라짐)" 같은 항목을 낸다. 지금 지원하지 않는 것(DB 자동 생성 M7, 워커)은 "마법사가 아직 만들어 주지 못함"이라고 **솔직히** 표시한다 |
| I-05 | 비용 범위 | 서버 | 서버 | 신규 | 사양(CPU, 메모리) × 실행 시간 + 고정 비용을 **범위**로 보여 준다. 트래픽이 없으면 정확히 계산할 수 없으므로 "기본 유지비" 범위와 "트래픽에 따라 늘어남"을 같이 쓴다. 단가표는 날짜와 함께 기록해 두고 화면에 기준일을 표시한다 (`D10`) |
| I-06 | 확신도 | 서버 | 서버 | 신규 | `high/medium/low`. 신호가 적거나, 이름을 못 찾았거나, 분류가 `unknown`이 많으면 낮춘다. 낮으면 "추정입니다"를 눈에 띄게 표시 |
| I-07 | 근거 설명 | 서버 | 서버 | 신규 | 판정에 쓴 신호를 한국어 문장으로 나열한다. 문장은 템플릿으로 만들고, 문장 다듬기에만 AI를 쓸 수 있다 (선택, 꺼도 동작) |
| I-08 | 사양 고르기 | ● | ● | 신규 | 사용자가 추천을 그대로 쓰거나 다른 수준을 직접 고른다. 고른 값이 배포의 CPU·메모리가 된다 |
| I-09 | 결과 저장 | 서버 | 서버 | 신규 | 배포를 만들 때 고른 수준, CPU, 메모리, 추천 결과(JSON)를 저장한다. 나중에 "추천과 실제가 달랐나"를 볼 수 있다 |

### 읽는 곳과 알 수 있는 것

| 읽는 곳 | 신호 | 사양·비용에 미치는 영향 |
|---|---|---|
| 의존성 파일 (`requirements.txt`, `package.json`) | 무거운 라이브러리 (`torch`, `tensorflow`, `opencv`, `pandas`, `puppeteer`, `playwright` 등) | 메모리 상향 |
| 같은 파일 | DB·캐시·큐 라이브러리 (`sqlalchemy`, `prisma`, `mongoose`, `psycopg2`, `redis`, `celery`, `bull`) | "DB/캐시/워커 필요" 항목 |
| `docker-compose.yml` | 서비스 개수와 종류 (db, redis, worker) | 필요한 것 목록. 가장 정확한 단서 |
| 환경변수 분류 결과 (H절) | `database`, `cache`, `external_api` 종류의 개수 | 필요한 것 목록, 확신도 |
| 프레임워크 설정 (Next.js `output: export`, Vite 정적 빌드) | 정적 사이트인지 서버가 필요한지 | 정적이면 서버 없이 가능하다는 안내 |
| scripts / `Procfile` / cron 흔적 | 백그라운드 작업 | "웹 서버 하나로는 안 됨" 표시 |
| 진입 파일 | 업로드 저장, 웹소켓, 로컬 파일 쓰기 | 디스크 휘발 경고 |
| 기존 `Dockerfile` | 베이스 이미지, `EXPOSE`, 빌드 단계 크기 | 사양 보정 |
| 파일 수·의존성 개수·트리 크기 | 앱 규모 | 수준 보정 (작은 가중치) |

읽지 않는 것: 소스 전체, lock 파일, 테스트, `node_modules`, `.env`와 키 파일. 한 번에 AI에 보내는 양은 지금 상한(트리 400줄, 파일 12,000자)을 넘지 않는다.

### 수준 표현 (숫자는 구현 때 채운다)

| 수준 | 대상 | CPU·메모리 | 월 비용 범위 |
|---|---|---|---|
| `small` | 가벼운 API, 정적 사이트 | (Express Mode 허용 조합 확인 후) | (단가표 확인 후) |
| `medium` | 일반 웹앱, 약한 계산 | (확인 후) | (확인 후) |
| `large` | 무거운 라이브러리, 큰 처리량 | (확인 후) | (확인 후) |

**숫자를 일부러 비워 두었다.** Express Mode가 허용하는 CPU·메모리 조합은 `HISTORY.md`의 열린 질문이고(최소값과 형식 미확인), 요금 구성(로드밸런서 비용 포함 여부 등)도 확인 전이다. 지어낸 숫자를 화면에 단정으로 보여 주면 안 된다 (규칙 2의 취지).

### 하지 않는 것
- 실제 트래픽 예측. "기본 유지비" 범위까지만 말한다.
- 자동으로 사양을 바꾸기. 사양 변경은 계속 확인을 받는다 (규칙 3).
- 사용자 코드를 고치라고 지시하기.

## G. 공통 규칙

- 서버의 `detail`(한국어)을 그대로 보여 준다.
- 파괴적 동작은 빨간 테두리와 확인 대화상자, 기본 포커스는 안전한 쪽.
- 열린 질문 대신 버튼 2~3개.
- 상태값 문자열은 한 곳(`constants`)에서만 정의하고, 웹과 앱이 같은 이름을 쓴다.
- 서버 필드 이름은 그대로 쓴다 (`d_id`, `repo_url`).
