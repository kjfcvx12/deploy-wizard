# Web Incident, Notification and Deploy-Settings Screens (Plan E) — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** The web UI gets the same operations screens the Expo app got in Plan D2: incident detail (S-13) with cause, where to fix, "what the wizard did" timeline and a 24-hour health bar; a problem banner, health dot and incident card on the deploy list/detail (S-02/S-04); per-deploy switches for auto-redeploy and auto-recovery (S-14); the notification list with an unread badge in the top bar (S-12); notification settings (S-15, without login).

**Architecture:** No backend change. Two new UI feature folders, `features/incidents/ui/` and `features/notifications/ui/`, plus additions to `features/deploys/ui/` (settings page, banner/dot/card pieces, two api methods) and `shared/ui/` (time helpers, polling hook, switch row, `request` error status). Pure logic (time, health buckets, timeline, labels, link/route rules, settings reading, backoff) lives in small DOM-free modules covered by Node's built-in test runner (`node --test`, no new dependency); components are verified in a real browser with `/api` mocked. Behavior and Korean copy are taken from the app screens (`app/app/incidents/[i_id].js`, `notifications.js`, `notification-settings.js`, `deploy-settings/[d_id].js`, `app/src/ops/*`, `app/src/components/ops/*`) — copy the strings from there, do not retype them from memory.

**Tech Stack:** React 19, react-router-dom 7, Vite 8, plain CSS tokens. Tests: `node --test` (Node 22). Browser checks: Playwright MCP tools against `npm run dev`.

**Spec:** `docs/app-web/06-screens.md` (S-02, S-04, S-12, S-13, S-14, S-15), `docs/app-web/02-feature-spec.md` (D-07..D-09, E-03, E-04), `docs/api-spec.md` (the BUILT contract: Incidents, Notifications, `PATCH /settings`, `health-history`, `Deploy_Read.open_incident_id/open_incident_status/auto_recover/health_state`). Backend = Plan D1, app reference = Plan D2 (both merged in `test`).

## Global Constraints

- Follow `docs/conventions.md` (React section): screens in `features/<feature>/ui/`; components `PascalCase.jsx`, others `camelCase.js`; one `ui/api.js` per feature mirroring its router; server field names unchanged (`i_id`, `d_id`, `n_id`, `fix_where`, `open_incident_status`, `auto_recover`, …); colors/spacing only via CSS variables of `shared/ui/styles.css` (no hard-coded colors); status strings defined once per feature in its `constants.js`; polling uses an `alive` flag/sequence + `clearTimeout`.
- Language: UI text Korean; code comments Korean one-liners above functions/components, no docstrings; identifiers English; JS style as existing files (2-space, no semicolons, single quotes). HISTORY/worklog terse English.
- Hard rule 3: the web never performs an automatic action. Incident screens show what the wizard did (restart / rollback) as read-only history; every change is a user-pressed button; stop is behind a confirmation dialog whose default focus is the safe option ("그대로 두기"). Hard rule 6: render `explain`, `summary`, action `detail` as text only (React escaping; never `dangerouslySetInnerHTML`); never show `evidence`; no tokens in URLs/`localStorage`/console.
- Server times are UTC **without** `Z`: always read them through `shared/ui/time.js` `toMs`.
- Statuses/kinds exactly as the backend: incident `open|recovering|resolved|needs_action`; incident kinds `unhealthy|crash_loop|bad_release|unknown`; notification kinds `incident_opened|incident_recovered|incident_needs_action|deploy_succeeded|deploy_failed|new_commit`; recovery action `restart|rollback`, result `running|ok|failed`; `health_state` `healthy|unhealthy|unknown`. Unknown values from the server must render as their raw string, never crash.
- Scope: the web does NOT do push (no device registration — S-17 is app only), login, "내 정보", delete-from-incident-page, an operations agent, or offline cache. Backend, `app/`, `tests/*.py`, `docs/api-spec.md` are not changed (no API change).
- Phone width 390 px must work: no horizontal page scroll, long `fix_where`/ARNs/URLs wrap, touch targets ≥ 40 px (existing phone rule `button, input, select { min-height: 40px }`), light and dark.
- Git: branch `feat/web-ops` from `test` (already created); Conventional Commits, Korean body, end with `Co-Authored-By: Claude Sonnet 5.5 <noreply@anthropic.com>`; never push; one commit per task.
- Verification: `node --test tests/web/` (logic), `npm run build`, and Playwright at 1280×800 and 390×844, light and dark (`browser_emulate_media`), `/api/**` mocked with `page.route` (fixtures below). State plainly at the end that nothing ran against the real backend, AWS, SMTP or a device. Never run two test runners at once; stop only the processes you started (by port listener PID — other projects share this PC); screenshots only under the system temp directory; no `.playwright-mcp/` left in the repo.

## Review Focus

- Incident detail with `explain` null / partial / `actions: []`, very long `fix_where`, and a browser where `navigator.clipboard` is missing (plain-http origin): the page renders, copy failure shows `고칠 곳을 복사하지 못했습니다`, the text stays selectable (Task 2).
- Polling lifecycle: the incident page refreshes every 5 s only while `open`/`recovering`, stops at `resolved`/`needs_action` and on 404 (Korean "찾을 수 없습니다" + a way back), backs off on network errors, pauses while the tab is hidden, and leaves no timer after navigating away; the top-bar unread count never piles up requests or shows an error (Tasks 2, 5).
- Time handling: UTC-without-Z strings show local time; unreadable/missing times render as empty text, not `Invalid Date`; the health bar still shows the newest checks when the browser clock is behind the server (Tasks 1, 2).
- Notification list: optimistic read and read-all roll back on failure and show the server message; double click sends one request; the `after` cursor never duplicates rows; a row whose `d_id`/`i_id` is missing or invalid only marks read; a link to a deleted deploy/incident lands on the 404 message (Task 5).
- Settings switches (deploy and notification): a failed PATCH restores only that switch and shows the server `detail`; only the changed field is sent; a switch is locked while its request is in flight; the `kinds` list is always sent whole, in server order; a late response after leaving the page changes nothing (Tasks 4, 6).
